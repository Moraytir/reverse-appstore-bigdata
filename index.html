Judging the Judge — A Hypothesis-Driven Study of App Store Success Signals

Apple ไม่เคยเปิดเผยเกณฑ์การจัดอันดับหรือคัดเลือกแอปให้ขึ้น Feature บน App Store โปรเจคนี้ใช้ข้อมูลเมทาดาทาของแอปกว่า 1.2 ล้านรายการ เพื่อทดสอบสมมติฐานว่า ปัจจัยเชิงพฤติกรรมของนักพัฒนาแบบใดสัมพันธ์กับความสำเร็จที่วัดได้จริง — โดยระบุขอบเขตและข้อจำกัดของข้อมูลไว้อย่างชัดเจนตั้งแต่ต้น

01

โจทย์ & ผู้ใช้คำตอบ

คำถามหลัก: ปัจจัยใดสัมพันธ์กับแอปที่มี engagement และคะแนนสูงผิดปกติเมื่อเทียบใน genre เดียวกัน — ไม่ใช่การยืนยันว่า Apple ใช้ปัจจัยเหล่านี้ในการตัดสินใจจริง เพราะข้อมูลที่มีไม่มี ranking หรือประวัติการ feature ให้ตรวจสอบได้ (ดูเหตุผลเต็มในหัวข้อ ข้อจำกัดของข้อมูล)

01 · Indie Developer

ตัดสินใจเชิงกลยุทธ์

ใช้ผลลัพธ์ประกอบการตั้งราคา ความถี่ในการอัปเดต และเลือก genre — โดยเข้าใจว่าเป็น correlation ไม่ใช่สูตรสำเร็จ

02 · Publisher / Investor

ประเมินความเสี่ยง

ใช้ pattern ที่พบเป็นสัญญาณประกอบการประเมิน ไม่ใช่กฎตายตัวของ Apple

03 · Regulator

ตรวจสอบ bias เชิงโครงสร้าง

ดูว่า developer รายใหญ่มีความได้เปรียบเชิงสถิติหรือไม่ ในบริบทประเด็น antitrust

02

ทำไมต้องใช้ Big Data

เหตุผลที่แก้ไขแล้ว — อิงจากลักษณะ workload จริง ไม่ใช่แค่ขนาดไฟล์

01

Group-by ระดับ Genre และ Developer ที่มี cardinality สูง

Normalize รายแอปเทียบภายใน genre เดียวกัน (หลายพัน genre) และ aggregate ระดับ DeveloperId (หลายแสนราย) ซ้ำหลายรอบตลอด pipeline — เป็น workload ที่ parallelize ได้ประโยชน์จริง ต่างจากการโหลดไฟล์เฉยๆ

02

Cross-correlation หลัง encode เฉพาะ numeric/categorical columns

ตัด column ที่เป็น free text (App_Name, URL, Developer) ออกก่อน แล้วรัน correlation matrix บนฟีเจอร์ที่ประมวลผลได้จริงบน 1.2M แถว

03

Iteration speed ระหว่างพัฒนา feature และ dashboard

การ query ซ้ำๆ ระหว่าง iterate บนข้อมูลเต็มจำนวน ได้ประโยชน์จาก Spark มากกว่าการรอ Pandas โหลดใหม่ทุกครั้ง

04

Anomaly detection ที่ต้องสแกนทุกแถวพร้อมกัน

หา traction pattern ผิดปกติเทียบ genre baseline ทั่วทั้ง dataset โดยไม่ sample ทิ้ง เพื่อไม่ให้พลาด anomaly ที่หายาก

ตัดออกจากฉบับเดิม
"ไฟล์ขนาด 1.5GB โหลดบน single machine ช้ามาก" และ "Permutation test บน 1.2M rows ใช้เวลาเป็นชั่วโมง" — ทั้งสองข้อไม่จริงเสมอไป เครื่องทั่วไปโหลด CSV 1.5GB ด้วย Pandas ได้ และ permutation test บน aggregated statistic รันด้วย NumPy ได้ในไม่กี่นาที จึงไม่ใช่เหตุผลที่ defend ได้เมื่อถูกซักถาม

04

Method & Pipeline

01

Ingest & Clean

โหลดผ่าน kagglehub เข้า PySpark ด้วย schema กำหนดชัด ลบ App_Id ซ้ำ ตรวจ consistency ระหว่าง Free/Price และ flag แถวที่ Updated เกิดก่อน Released

02

Feature Engineering

Rating Drift (Current_Version_Score − Average_User_Rating), Update Recency Ratio (Days_Since_Update / App_Age), Developer Size Bucket, Composite Trust Score, และ Relative Rating in Genre (z-score) เพื่อควบคุม genre confounder

03

Statistical Analysis

Spearman correlation ต่อ genre-normalized metric, Permutation Test พร้อม multiple-testing correction, Anomaly Detection บน traction rate ที่ผิดปกติเทียบ genre baseline

⚠ ผลลัพธ์คือ "traction anomaly" ไม่ใช่ "หลักฐานการถูก feature"
04

Output

สรุปน้ำหนักสัมพัทธ์ของแต่ละปัจจัยต่อ engagement ที่สูงผิดปกติ พร้อม Dashboard เชิง interactive — นำเสนอเป็น "hypothesis ที่ทดสอบแล้ว" ไม่ใช่ "algorithm ที่ถอดได้"

05

Evaluation — Correction Log

เกณฑ์ประเมินผลฉบับเดิมมี 2 ใน 4 ตัวที่วัดไม่ได้จริงด้วยข้อมูลที่มี — แก้ไขดังนี้

Metric 01 · Correlation Significance Statistical flaw
เดิม

p-value < 0.05 = "Good Enough"

แก้ไข

ต้องรายงาน effect size ควบคู่เสมอ — เกณฑ์ผ่านคือ |Spearman's ρ| ≥ 0.15 และ p < 0.05 หลัง correction เพราะ n = 1.2M ทำให้ correlation จิ๋วก็ significant ได้เสมอ

Metric 02 · Anomaly Detection Precision Unmeasurable
เดิม

Precision > 70%

แก้ไข

ไม่มี ground truth ให้คำนวณ precision ได้จริง — เปลี่ยนเป็น manual validation: สุ่มตรวจ anomaly ที่ตรวจพบ 25–30 รายการ ให้ทีมยืนยันความสมเหตุสมผลด้วยตา (qualitative agreement rate)

Metric 03 · Factor Weight Accuracy Undefined method
เดิม

"Top 3 factors ชัดเจน" — ไม่ระบุวิธีคำนวณ weight

แก้ไข

ระบุ method ชัดเจน: Feature Importance จาก Random Forest ทำนาย proxy-success label พร้อม SHAP values — รายงานลำดับความสำคัญพร้อมช่วงความเชื่อมั่น

Language Fix · "Featured" Wording Overclaim
เดิม

"Rating พุ่งผิดปกติ = เพิ่ง featured"

แก้ไข

เปลี่ยนเป็น "traction anomaly" ทุกจุดในเอกสาร — รายงานเป็นสมมติฐานที่ยังพิสูจน์ไม่ได้ เพราะการโตของ reviews มีสาเหตุอื่นได้มาก (การตลาด, ไวรัล, การแก้บั๊ก)

06

ข้อจำกัดของข้อมูล — Limitations Ledger

รายการข้อจำกัดที่ต้องระบุไว้ในทุกส่วนของรายงาน ไม่ใช่แค่ท้ายเล่ม

✕ No Ground Truth

Dataset ไม่มี ranking, chart position, หรือประวัติการ feature — ทุกข้อสรุปเป็น correlation กับ proxy metric เท่านั้น ไม่ใช่การเข้าถึง algorithm จริง

✕ Survivorship Bias

เห็นเฉพาะแอปที่ยังอยู่บน Store ตอน scrape ไม่มีแอปที่ถูก reject หรือถอดออก ผลลัพธ์อาจสะท้อน "อะไรทำให้รอด" มากกว่า "อะไรทำให้ถูกเลือก"

⚠ Genre Confounder

Rating baseline ต่างกันตาม genre โดยธรรมชาติ — ทุก metric ต้อง normalize ภายใน genre ก่อนเปรียบเทียบ ไม่เช่นนั้นผลลัพธ์อาจเป็นแค่ genre effect

⚠ Multicollinearity

Trust Score และ Developer Size น่าจะสัมพันธ์กันเอง (publisher ใหญ่มักมี website) ต้องเช็ค correlation matrix ระหว่าง feature เองก่อนตีความ importance

⚠ Missing Data ไม่ Random

Developer_Website ที่เป็น null มักเป็น developer รายเล็ก — encode เป็นสัญญาณ (มี/ไม่มี) แทนการ drop เพื่อไม่ให้ dataset เอียงไปทาง publisher ใหญ่

○ Reproducibility

Permutation test มี randomness — ต้อง fix random seed, ใช้ Git ตลอดโปรเจค และเขียน environment file เพื่อให้รันซ้ำได้ผลตรงกัน

Scope & Risks

In Scope

Data cleaning · Feature engineering · Genre-normalized statistical analysis · Anomaly detection (qualitative validation) · Interactive dashboard

Out of Scope

Real-time App Store data · Apple API access · Sentiment analysis จาก review text · ข้อมูลรายได้ · การยืนยัน algorithm จริงของ Apple

Technical
PySpark setup ยากสำหรับบางคนในทีม
ใช้ Google Colab + PySpark หรือ Databricks Community Edition เป็นทางเลือก
Technical
Permutation test ช้าเกินไปบนข้อมูลเต็ม
ลด sample เป็น 200K rows ที่ stratified sample ตาม genre แล้วรายงานช่วงความเชื่อมั่น
Methodology
ผลลัพธ์อาจเป็นแค่ genre effect ไม่ใช่ effect จริงของ feature
บังคับ normalize-by-genre ตั้งแต่ feature engineering ไม่ใช่แก้ทีหลังตอนพบผลแปลก
Methodology
ทีมพึ่งพา proxy label ไม่ตรงกัน ทำให้งาน 4 กลุ่มต่อกันไม่ได้
Freeze คำนิยาม proxy success label ในสัปดาห์แรกก่อนแตะโค้ด แจกเอกสาร 1 หน้าให้ทุกคน
Methodology
Anomaly ไม่ชัดเจนหรือ noise เยอะ
ใช้ Isolation Forest แทน rule-based threshold และ validate ด้วยการสุ่มตรวจด้วยตา
